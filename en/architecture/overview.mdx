# Architecture overview

OpenYida is a Node.js CLI that lets AI coding agents operate the Yida low-code platform. It does not run an LLM service itself. Instead, it gives tools such as Codex, Claude Code, Cursor, Qoder, and Wukong a stable command surface for creating apps, forms, custom pages, reports, connectors, integrations, and data operations.

## Layers

```
AI coding agent
  -> openyida CLI
  -> local project workspace
  -> Yida web APIs with cached login cookies
  -> Yida low-code app, form, page, report, or data result
```

| Layer | Source path | Responsibility |
| --- | --- | --- |
| CLI entry | `bin/yida.js` | Parse commands and route to implementation modules. |
| Core utilities | `lib/core/` | Environment detection, i18n, update checks, workspace copy, data/query helpers, and Babel transforms. |
| Authentication | `lib/auth/` | Login, cookie cache, QR handoff, organization switching, and multi-environment support. |
| App and page management | `lib/app/` | Create apps, create forms, create custom display pages, list pages, check, compile, and publish custom pages. |
| Page sharing | `lib/page-config/` | Verify short URLs and save public or organization share config. |
| Permissions | `lib/permission/` | Read and save form permission groups. |
| Process and automation | `lib/process/`, `lib/integration/` | Create process forms, configure process rules, preview instances, and create integration flows. |
| Connectors and reports | `lib/connector/`, `lib/report/` | Manage HTTP connectors and native Yida reports. |
| Skills | `yida-skills/` | Markdown instructions used by AI agents to choose the right CLI workflow. |

## Project workspace

`openyida copy` initializes a local workspace that agents can read and update:

```text
project/
  config.json
  pages/
    src/
    build/
    dist/
  .cache/
```

- `config.json` stores app and organization context.
- `pages/src/` stores custom page source files.
- `pages/build/` and `pages/dist/` store compiled output.
- `.cache/` stores local metadata such as schemas and login cache files.

## Custom page pipeline

Custom display pages use Yida-compatible React 16 style source files.

```bash
openyida create-page <appType> "Dashboard"
openyida check-page project/pages/src/dashboard.oyd.jsx
openyida compile project/pages/src/dashboard.oyd.jsx
openyida publish project/pages/src/dashboard.oyd.jsx <appType> <formUuid>
```

`create-page` returns the page `formUuid`. Agents should use the returned value and should never invent IDs.

## Authentication and environments

OpenYida stores login state in the active project cache and sends Yida requests with cached cookies. The active environment can be public cloud, overseas, or a private deployment.

```bash
openyida env --json
openyida login --check-only --json
openyida env <setup|list|show|switch|add|remove>
```

In Codex and other AI coding environments, OpenYida prefers cached credentials first. If needed, it can use browser login, terminal QR login, or agent QR handoff.

## Data and schema discipline

Yida field IDs are generated by the platform. Before creating data, updating data, configuring query conditions, or writing custom page code against form data, agents should run:

```bash
openyida get-schema <appType> <formUuid>
```

Data operations use the unified `openyida data` command. Global task-center queries use `openyida task-center` and do not require an `appType`.

## Machine-readable command manifest

The CLI exposes its current command surface for agents and documentation checks:

```bash
openyida commands --json
```

Docs should prefer this manifest over hand-maintained command lists whenever possible.
