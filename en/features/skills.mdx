## Environment & authentication

```bash
# Environment check
openyida env
openyida env --json

# Multi-environment management
openyida env setup                 # Configure public, overseas, intranet, or private deployment presets
openyida env list                  # List all environments, highlight the active one
openyida env add <name>            # Interactively add a private deployment environment
openyida env switch <name>         # Switch the active environment
openyida env remove <name>         # Remove an environment (cannot remove "public")
openyida env show [name]           # Show detailed environment configuration

# Login
openyida login [--qr|--agent-qr|--codex|--browser] [--env <name>|--intl|--overseas|--global|--yidaapps] [--corp-id <corpId>]
openyida login --check-only --json # Check the current login state only

# Logout
openyida logout

# Auth management
openyida auth status               # Check login status
openyida auth login                # Perform login
openyida auth refresh              # Refresh session
openyida auth logout               # Logout

# Organization management
openyida org list                  # List accessible organizations
openyida org switch --corp-id <id> # Switch organization

# Initialize workspace
openyida copy [--force]            # Copy project directory (flattens into empty dirs)
openyida copy -skills              # Copy yida-skills to AI tool skills directory

# Diagnostic tools
openyida doctor [--fix]            # Environment diagnosis
openyida doctor --monitor          # Health monitoring
openyida doctor --report <format>  # Generate report (json|markdown|html)

# Self-update
openyida update                    # Check for and install the latest version

# Machine-readable command manifest
openyida commands --json           # Print the current CLI manifest
```

## Application management

```bash
# List applications
openyida app-list [--size N]

# Create application
openyida create-app "<name>" [desc] [icon] [color] [themeColor] [--open|--no-open]
openyida create-app --name "<name>" [--desc "<description>"] [--theme deepBlue] [--open|--no-open]

# Export application
openyida export <appType> [output] # Generate migration package

# Import application
openyida import <file> [name]      # Rebuild app from migration package

# Update application info
openyida update-app <appType> --name "<name>" [--desc "<description>"] [--icon "<icon>"] [--icon-color "<color>"]

# Manage application-level permissions
openyida app-permission <get|set|add|remove|search-user> ...
```

| Option | Alias | Description |
|--------|-------|-------------|
| `--name` | `-n` | App name (at least one update field required) |
| `--desc` | `-d` | App description |
| `--icon` | | Icon name (e.g. `xian-yingyong`) |
| `--icon-color` | | Icon color (default: `#0089FF`) |

### Application permissions

Manage the members shown in Yida **App settings → Permission management**.

```bash
openyida app-permission search-user <keyword> [--dept <text>] [--size N]
openyida app-permission get <appType>
openyida app-permission set <appType> <main|data|dev> --users <userId1,userId2>
openyida app-permission set <appType> <data|dev> --clear
openyida app-permission add <appType> <main|data|dev> --users <userId1,userId2>
openyida app-permission remove <appType> <main|data|dev> --users <userId1,userId2>
```

| Role | Meaning | Notes |
|------|---------|-------|
| `main` | Primary app admins | Cannot be empty |
| `data` | Data admins | Can be cleared |
| `dev` | Developer members | Can be cleared |

## Form management

```bash
# Create form
openyida create-form create <appType> "<form name>" <fieldsJSON> \
  [--layout <layout>] \
  [--theme <theme>] \
  [--label-align <alignment>]

# Update form
openyida create-form update <appType> <formUuid> <changesJSON> [--force]

# Add options to a SelectField, RadioField, CheckboxField, or MultiSelectField
openyida create-form add-option <appType> <formUuid> <fieldLabel> <option1> [option2] ...

# Get form schema (required before any field ID operation)
openyida get-schema <appType> <formUuid>
openyida get-schema <appType> --all [--output-dir <dir>]
openyida get-schema <appType> <formUuid> --field <labelOrFieldId> [--json]

# Update form config
openyida update-form-config <appType> <formUuid> <isRenderNav> <title>

# List form pages in an application
openyida list-forms <appType> [--keyword <text>]
```

<Warning>
  Field IDs in Yida are randomly generated by the platform (e.g. `textField_eftt1aa5m`, `selectField_fix024y92`) and cannot be inferred from field names. You **must** run `openyida get-schema` to obtain the real field IDs before performing any operation that references them — including creating or updating form data, configuring query conditions, and writing custom pages.
</Warning>

<Info>
  When updating a form that already contains data, the CLI performs a safety check before applying changes. If existing records are detected and `--force` is not set, the command outputs a JSON response with `requiresConfirmation: true` and exits without making changes. Pass `--force` to skip confirmation and proceed with the update.

  The confirmation response includes:

  | Field | Type | Description |
  |-------|------|-------------|
  | `success` | `boolean` | Always `false` when confirmation is required |
  | `requiresConfirmation` | `boolean` | Always `true` |
  | `formUuid` | `string` | The form UUID being updated |
  | `appType` | `string` | The application ID |
  | `existingDataCount` | `number` | Number of existing records in the form |
  | `message` | `string` | Human-readable confirmation message |
  | `hint` | `string` | Usage hint showing the `--force` flag syntax |
</Info>

### List form pages

Retrieve all form pages within an application, optionally filtered by keyword. The command outputs a JSON array of form entries to stdout.

```bash
openyida list-forms <appType> [--keyword <text>]
```

| Argument | Description |
|----------|-------------|
| `<appType>` | Application ID (e.g. `APP_XXXXX`) |

| Option | Description | Default |
|--------|-------------|---------|
| `--keyword <text>` | Filter forms by name, UUID, type, or path name (case-insensitive) | — |

#### Output

The command prints a JSON array to stdout. Each entry has the following shape:

| Field | Type | Description |
|-------|------|-------------|
| `formUuid` | `string` | Unique form identifier |
| `formName` | `string` | Localized form name |
| `formType` | `string` | Form type (e.g. `display`, `process`) |
| `pathName` | `string` | URL path name of the form |

**Example output:**

```json
[
  {
    "formUuid": "FORM-AAA",
    "formName": "Customer Info",
    "formType": "display",
    "pathName": "customer-info"
  },
  {
    "formUuid": "FORM-BBB",
    "formName": "Expense Report",
    "formType": "process",
    "pathName": "expense"
  }
]
```

**Examples:**

```bash
# List all forms in an application
openyida list-forms APP_XXXXX

# Filter by keyword
openyida list-forms APP_XXXXX --keyword "customer"
```

<Info>
  System navigation items (e.g. built-in task views) are automatically excluded from the output. Only user-created form pages are returned.
</Info>

<Info>
  You must be logged in before running this command. Run `openyida login` first if you have not authenticated.
</Info>

## Data management

<Warning>
  Before creating or updating data, you **must** run `openyida get-schema` to obtain the real field IDs. After creating or updating a record, verify the data by running `openyida data query form <appType> <formUuid> --size 1` and confirming that `formData` fields contain actual values. If all fields are empty, the field IDs are incorrect and need to be re-checked via `get-schema`.
</Warning>

```bash
# Unified data management
openyida data <action> <resource> [args]

# Form data
openyida data query form <appType> <formUuid> [--page N] [--size N] [--search-json JSON|--search-file .cache/openyida/search.json] [--inst-id ID]
openyida data get form <appType> --inst-id <id>
openyida data create form <appType> <formUuid> (--data-json <JSON>|--data-file .cache/openyida/data.json)  # JSON keys can be field IDs or field labels
openyida data update form <appType> --inst-id <id> (--data-json <JSON>|--data-file .cache/openyida/data.json)

# Process data
openyida data query process <appType> <formUuid> [--page N] [--size N] [--search-json JSON|--search-file .cache/openyida/search.json] [--task-id ID] [--instance-status STATUS] [--approved-result RESULT]
openyida data get process <appType> --process-inst-id <id>
openyida data create process <appType> <formUuid> --process-code <code> (--data-json <JSON>|--data-file .cache/openyida/data.json)
openyida data update process <appType> --process-inst-id <id> (--data-json <JSON>|--data-file .cache/openyida/data.json)
openyida data query operation-records <appType> --process-inst-id <id>

# Task management
openyida data query tasks <appType> --type <todo|done|submitted|cc> [--page N] [--size N] [--keyword TEXT] [--process-codes JSON] [--instance-status STATUS]
openyida data execute task <appType> --task-id <id> --process-inst-id <id> --out-result <AGREE|DISAGREE> --remark <text> [--data-json JSON|--data-file .cache/openyida/data.json] [--no-execute-expressions y]

# Subform
openyida data query subform <appType> <formUuid> --inst-id <id> --table-field-id <fieldId>
```

## Global task center

Query the current user's global task center data without specifying an `appType`.

```bash
# Todo tasks
openyida task-center todo [--page N] [--size N] [--keyword TEXT]

# Created by me
openyida task-center created [--page N] [--size N] [--keyword TEXT] [--no-detail]

# Done tasks
openyida task-center done [--page N] [--size N] [--keyword TEXT]

# CC'd to me
openyida task-center cc [--page N] [--size N] [--keyword TEXT]

# Submitted by proxy
openyida task-center proxy [--page N] [--size N] [--keyword TEXT]
```

### Task types

| Type | Description | API endpoint |
|------|-------------|--------------|
| `todo` | Tasks pending your action | `getTodoTasksInCorp` |
| `created` | Tasks you initiated | `getMyCreateInCorp` |
| `done` | Tasks you have processed | `getDoneTasksInCorp` |
| `cc` | Tasks CC'd to you | `getNotifyMeInCorp` |
| `proxy` | Tasks submitted on your behalf | `getSubmitAgentInCorp` |

### Optional parameters

| Parameter | Description | Default |
|-----------|-------------|---------|
| `--page N` | Page number | `1` |
| `--size N` | Items per page (max 100) | `20` |
| `--keyword TEXT` | Search keyword | — |
| `--no-detail` | Omit detail data (only supported for `created` type) | — |

<Info>
  Unlike `openyida data query tasks`, the `task-center` command queries global task center data and does not require an `appType` parameter.
</Info>

### Process instance preview

Generate an interactive HTML flowchart for a running or completed process instance. The flowchart highlights node statuses — completed (green), current (blue pulse), pending (grey), and skipped (dashed) — and shows approver details and timestamps on hover.

```bash
openyida process preview <appType> <processInstanceId> [--output <path>]
```

| Argument | Description |
|----------|-------------|
| `<appType>` | Application ID (e.g. `APP_XXXXX`) |
| `<processInstanceId>` | Process instance ID to visualize |

| Option | Alias | Description | Default |
|--------|-------|-------------|---------|
| `--output` | `-o` | Output file path for the generated HTML | Auto-generated in current directory |

The command fetches the process instance details and operation records, then generates an SVG-based HTML file and opens it in your default browser.

**Example:**

```bash
openyida process preview APP_XXXXX proc-inst-id-xxx
openyida process preview APP_XXXXX proc-inst-id-xxx --output flowchart.html
```

<Info>
  You must be logged in before running this command. Run `openyida login` first if you have not authenticated.
</Info>

### Process definition detail URL properties

The process definition JSON file supports the following optional properties for customizing the detail page URL that users see when viewing a process instance.

| Property | Type | Description |
|----------|------|-------------|
| `processDetailUrl` | `string` | Custom URL for the web/PC process detail page. Overrides all other detail URL settings for web. |
| `processMobileDetailUrl` | `string` | Custom URL for the mobile process detail page. Overrides all other detail URL settings for mobile. |
| `customDetailPageUrl` | `string` | A single custom page URL used for both web and mobile detail pages. On mobile, `?procInsId=` is appended automatically. |
| `detailUrls` | `object` | An object with platform-specific detail URLs. Supports `web` (or `pc`) and `mobile` keys. |

The resolution order for the **web detail URL** is:

1. `processDetailUrl`
2. `detailUrls.web` or `detailUrls.pc`
3. `customDetailPageUrl`
4. Platform default

The resolution order for the **mobile detail URL** is:

1. `processMobileDetailUrl`
2. `detailUrls.mobile`
3. `customDetailPageUrl` (with `?procInsId=` appended)
4. Platform default

**Example** using `detailUrls`:

```json
{
  "detailUrls": {
    "web": "https://example.com/process/detail",
    "mobile": "https://m.example.com/process/detail"
  }
}
```

**Example** using `customDetailPageUrl` (same URL for both platforms):

```json
{
  "customDetailPageUrl": "https://example.com/custom-detail"
}
```

### Error handling and retry

If process configuration fails after the form has already been created, the command outputs a retry hint with the `--formUuid` flag so you can reuse the form without recreating it:

```bash
openyida create-process <appType> --formUuid <formUuid> <processDefinitionFile>
```

This is useful when:
- The process definition file contains errors that need to be fixed before retrying.
- A transient network or API failure interrupted the configuration step.

The command outputs a JSON result to `stdout`. On success:

```json
{
  "success": true,
  "formUuid": "FORM-XXXXX",
  "formTitle": "Order Form",
  "appType": "APP_XXXXX",
  "fieldCount": 5,
  "processCode": "TPROC-XXXXX",
  "url": "https://www.aliwork.com/APP_XXXXX/workbench/FORM-XXXXX"
}
```

On failure (for example, when process configuration fails):

```json
{
  "success": false,
  "formUuid": "FORM-XXXXX",
  "formTitle": "Order Form",
  "appType": "APP_XXXXX",
  "fieldCount": 5,
  "error": "Failed to configure process: <error details>"
}
```

<Tip>
  When you see a failure with a `formUuid` in the output, use the `--formUuid` flag to retry without recreating the form.
</Tip>

## Integration & automation

Create and manage logicflows (integration & automation) that support form event triggers, message notifications, data operations, and more.

```bash
# Create a logicflow
openyida integration create <appType> <formUuid> <flowName> [options]
```

### Parameters

| Parameter | Required | Description |
|-----------|----------|-------------|
| `appType` | Yes | Application ID, e.g. `APP_XXXX` |
| `formUuid` | Yes | Trigger form UUID, e.g. `FORM-XXXX` |
| `flowName` | Yes | Logicflow name |

### Options

| Option | Default | Description |
|--------|---------|-------------|
| `--process-code <code>` | Auto-generated | Existing logicflow processCode (`LPROC-xxx` format) |
| `--receivers <userId,...>` | Empty | User IDs for DingTalk work notifications, comma-separated |
| `--title <title>` | Same as flowName | Notification title, supports `#{fieldId-ComponentType}#` field references |
| `--content <content>` | `"New form record submitted"` | Notification content, supports field variable references |
| `--events <insert,update>` | `insert` | Trigger events: `insert`/`update`/`delete`/`comment`, approval completion `processFinish`, or approval node `activityTask`; aliases `approval` and `approvalNode` are also supported |
| `--approval-actions <agree,...>` | — | Required for approval events. Values: `agree`, `disagree`, `terminated` |
| `--approval-node-ids <nodeId,...>` | — | Required for `activityTask`; filters approval node IDs |
| `--trigger-recursively` | `false` | Allow the flow to be triggered recursively |
| `--trigger-condition <fieldId:fieldName:opCode:value[:componentType[:valueType]]>` | — | Add trigger filtering conditions; can be specified multiple times |
| `--data-form-uuid <formUuid>` | — | Target form UUID for the get-single-data node |
| `--data-condition <bFieldId:bFieldName:aFieldId[:componentType]>` | — | Filter condition for get-single-data, can be specified multiple times |
| `--add-data-form-uuid <formUuid>` | — | Target form UUID for the add-data node |
| `--add-data-assignment <targetFieldId:valueType:value>` | — | Field assignment for add-data, can be specified multiple times. `valueType`: `processVar`/`literal`/`column` |
| `--connector-id <id>` + `--action-id <id>` | — | Add an HTTP connector call node; both options must be provided |
| `--connector-inputs <file>` | — | JSON file describing connector inputs for the canvas |
| `--connector-assignment <column:valueType:value>` | — | Connector input assignment; can be specified multiple times |
| `--publish` | Not published | Publish immediately after saving; otherwise saves as draft only |

### Examples

```bash
# Notify users when a form record is created
openyida integration create APP_XXX FORM-XXX "New record notification" \
  --receivers user123 \
  --title "New record submitted" \
  --content "A new form record has been submitted."

# Reference form field variables, save and publish
openyida integration create APP_XXX FORM-XXX "Record change notification" \
  --receivers user123,user456 \
  --events insert,update,delete,comment \
  --publish

# Sync data from form A to form B with an add-data node
openyida integration create APP_XXX FORM-A-XXX "Sync to form B" \
  --add-data-form-uuid FORM-B-XXX \
  --add-data-assignment "textField_b1:processVar:textField_a1" \
  --add-data-assignment "numberField_b2:literal:0" \
  --publish

# Approval completion event
openyida integration create APP_XXX FORM-XXX "Approval result notify" \
  --events processFinish \
  --approval-actions agree,disagree,terminated \
  --receivers user123 \
  --publish

# Approval node event
openyida integration create APP_XXX FORM-XXX "Node reminder" \
  --events activityTask \
  --approval-actions agree \
  --approval-node-ids node_123,node_456 \
  --receivers user123
```

### Field variable references

Use `#{fieldId-ComponentType}#` in notification titles and content to reference trigger form field values:

```
#{textField_mmq4ldti-TextField}#
#{numberField_abc123-NumberField}#
```

### Output

```json
{
  "success": true,
  "published": false,
  "processCode": "LPROC-XXXX",
  "flowName": "New record notification",
  "appType": "APP_XXX",
  "formUuid": "FORM-XXX",
  "formEventTypes": ["insert"]
}
```

<Info>
  You must be logged in before running this command. When `--publish` is used, `published` will be `true`; if publishing fails, `published` will be `false` with a `warning` field.
</Info>

## Flash note to PRD

Convert DingTalk flash notes (meeting transcripts) into structured PRD documents using AI.

```bash
# From file
openyida flash-to-prd --file <path> [--name <project name>] [--max-tokens <number>]

# From stdin
cat meeting.txt | openyida flash-to-prd --name <project name> [--max-tokens <number>]
```

### Parameters

| Parameter | Alias | Description | Default |
|-----------|-------|-------------|---------|
| `--file` | `-f` | Path to the flash note file | — |
| `--name` | `-n` | Project name (auto-detected from content if omitted) | — |
| `--max-tokens` | — | Maximum tokens for AI response | `8000` |

The command reads flash note content from the specified file or from stdin, preprocesses the text (including meeting metadata extraction and speaker identification), and calls the Yida AI service to generate a structured PRD. The output PRD file is saved to the `prd/` directory in your project.

### Output

The command prints a JSON result to stdout with the following shape:

```json
{
  "success": true,
  "projectName": "My Project",
  "prdFile": "/path/to/prd/My-Project.md",
  "contentLength": 4096,
  "meetingRecognition": {
    "metaFields": 3,
    "a1Sections": 2,
    "speakers": 5
  }
}
```

<Info>
  You must be logged in before running this command. Run `openyida login` first if you have not authenticated.
</Info>

## DingTalk CLI (dws)

Proxy commands to the DingTalk Workspace CLI for contacts, calendar, todo, approval, attendance, and more.

```bash
openyida dws <command> [args]
```

<Info>
  The `dws` command requires the DingTalk CLI to be installed separately. If it is not installed, OpenYida will prompt you to install it on first use.
</Info>

### Common commands

| Command | Description |
|---------|-------------|
| `contact user search --keyword "<name>"` | Search contacts |
| `calendar event list` | List calendar events |
| `todo task create --title "<title>" --executors "<userId>"` | Create a todo task |
| `approval instance list` | List approval instances |
| `attendance record list` | Query attendance records |
| `chat robot send --content "<message>"` | Send a chat robot message |

### Special commands

```bash
# Install DingTalk CLI
openyida dws install

# Show help
openyida dws help
```

### Output format

By default, output is formatted as a table for human readability. Add `-f json` for JSON output suitable for AI agents.

```bash
openyida dws contact user search --keyword "name" -f json
```

## Export conversation

Export AI conversation records from the current AI tool environment as Markdown documents.

```bash
openyida export-conversation [options]
```

### Options

| Option | Alias | Description | Default |
|--------|-------|-------------|---------|
| `--output` | `-o` | Output file path | Auto-generated path |
| `--input` | `-i` | Input conversation file (JSON/JSONL) | — |
| `--latest` | — | Export only the latest conversation | Enabled |
| `--list` | — | List available conversation records | — |

### Examples

```bash
# Export current conversation
openyida export-conversation
```

## Self-update

Check for a newer version of OpenYida on npm and install it globally.

```bash
openyida update
```

The command queries the npm registry for the latest published version. If a newer version is available, it runs `npm install -g openyida@latest` to upgrade in place. If you are already on the latest version, it prints a confirmation and exits.

<Info>
  OpenYida also checks for updates automatically in the background each time you run any command. The `update` command lets you trigger this check and install explicitly.
</Info>

## Environment variables

| Variable | Description | Example |
|----------|-------------|---------|
| `OPENYIDA_LANG` | Set language | `zh`, `en`, `ja` |
| `LANG` / `LC_ALL` | System language | `zh_CN.UTF-8` |
| `AGENT_WORK_ROOT` | Wukong workspace root path (dynamic UUID) | `~/.real/users/user-xxx/` |
| `OPENYIDA_ENDPOINT` | Override the Yida service endpoint (highest priority) | `https://yida.example.com` |
| `OPENYIDA_LOGIN_URL` | Override the login page URL | `https://yida.example.com/login` |
| `OPENYIDA_ENV` | Switch environment without modifying config (useful for CI/CD) | `my-private-env` |
| `OPENYIDA_DWS_ENDPOINT` | Private DingTalk OpenAPI gateway endpoint | `https://oapi.example.com` |

### Endpoint resolution priority

When resolving the Yida service endpoint, the following order applies:

1. `OPENYIDA_ENDPOINT` environment variable
2. Active environment configuration (set via `openyida env switch`)
3. Cached `base_url` from cookie
4. Default public cloud URL (`https://www.aliwork.com`)

Login URL resolution order:

1. `OPENYIDA_LOGIN_URL` environment variable
2. Active environment configuration
3. Default login URL (`https://www.aliwork.com/workPlatform`)
